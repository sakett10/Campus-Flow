# ADR-009: Notification architecture

## Status

Accepted

## Decision

Notifications are treated as **durable, auditable infrastructure**, not fire-and-forget side effects.

The MVP establishes the event model, lifecycle transitions, and notification dispatch abstraction. We do **not** claim that web push notifications constitute reliable cross-device delivery.

### Notification Lifecycle States

Every notification event must be traceable through explicit lifecycle states:

1. `created`: Notification intent generated by an agent or system event.
2. `scheduled`: Placed on queue with a target dispatch timestamp (respecting user study windows and quiet hours).
3. `attempted`: Worker has initiated dispatch to the notification transport channel.
4. `delivered`: Transferred and confirmed by the downstream transport/client. Enqueuing or initiating dispatch **must never be recorded as delivered**.
5. `opened`: User clicked or viewed the notification (when detectable).
6. `action_taken`: User executed the associated primary action (e.g., resumed focus session, opened exam plan).
7. `suppressed`: Notification was dropped due to active Focus Mode, quiet hours policy, or deduplication.
8. `failed`: Terminal failure with diagnostic error code after retry exhaustion.

### Core Capabilities

- **Deduplication & Idempotency**: Each notification intent carries a deterministic `dedupe_key`. Duplicate intents are dropped or merged before dispatch.
- **Priority Classification**: `low` | `standard` | `high` | `urgent`. Focus Mode defers low/standard priority notifications.
- **Diagnostics**: Detailed delivery records enabling full auditing and delivery diagnostics.

## Alternatives considered

- **Ad-hoc push calls in business code**: Untracked, impossible to debug why students missed study reminders, and prone to spamming.
- **Claiming enqueue is delivered**: Violates engineering rules ("A notification system must never claim delivery merely because a notification was requested").
- **Third-party SaaS as black box**: Hides delivery latency and lifecycle telemetry from student audit logs.

## Reason

Students depend on accurate study session reminders and deadline alerts. Treating notifications as a reliable state machine prevents spam, avoids broken quiet hours, and provides accountability.

## Consequences

- Notification intents are stored in PostgreSQL and scheduled via BullMQ delayed jobs.
- Focus Mode and quiet hours must be checked at both schedule time and dispatch time.

## Reversal conditions

Modify this lifecycle only if transport channels provide deeper or alternative verifiable receipt telemetry.
